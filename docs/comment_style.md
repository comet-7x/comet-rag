# 注释与 Docstring 标准

本项目参考 nanobot 的做法：代码承担“是什么”，注释只补代码无法表达的约束。
默认不写；删掉后不会丢失重要信息，就应删除。

## 该写什么

- 契约：调用前提、返回保证、异常、幂等性。
- 不变式：状态、并发、一致性与资源所有权。
- 反直觉原因：为什么更简单的写法会错。
- 外部限制：协议、安全边界或第三方库陷阱。

不要复述函数名、类型、控制流、字段描述或评审历史。

## 怎么写

- 模块、类和公开函数通常一句话；签名足够清楚时省略。
- 行内注释紧贴相关代码，先写结论，通常不超过三行。
- 源码注释不用 Markdown 标题、粗体或长列表。
- 长设计说明放到 `docs/`，源码只保留结论和稳定引用。
- 同一事实只保留一个权威位置；修改行为时同步更新。

## 各层关注点

| 位置 | 只在必要时说明 |
|---|---|
| `ports/` | 可替换实现共同遵守的契约 |
| `core/`、`tasks/` | 状态、并发、重试与一致性不变式 |
| `engines/` | 格式语义、确定性与降级行为 |
| `infrastructure/` | 外部协议、连接与资源生命周期 |
| `services/` | 跨组件编排与失败策略 |
| `api/`、`workers/` | HTTP、队列与进程边界 |

评审时只问三件事：它是否仍然正确；是否提供代码之外的信息；能否再短一半。
