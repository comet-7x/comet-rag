## 第三十五批：真实服务器链路

本机运行官方生产CLI的API、CPU和IO独立进程；使用任务自建PostgreSQL database、
Redis DB12、Milvus限定测试database内随机前缀和新的KB。MinIO/embedding/reranker
连接项目现有服务器配置，独立MinerU API连接现有VLM。没有连接未知生产SQL/Redis，
没有迁移、切换或删除服务器已有数据。

用户原PDF工作区副本9024767字节，SHA-256
`e42f3b70cee6344ca8e0cb06ccc4028e56a05266cbd331c9e008fe05e62a2ffe`。
原文件经MinIO精确key上传读取，源字节前后核验。实际Pipeline采用默认child2000/
overlap200字符和显式parent4000，区别于33批800/80/1600的质量实验。

验证顺序与断言：

1. 仅启动API/CPU，真实PDF提取后生成129个child、67个parent，并在TaskStore持久化
   indexing移交；此时active为空，CPU以0退出。
2. 重复同idempotency_key返回原task_id。新IO进程从既有handoff继续，真实向量化、
   Milvus写入及激活成功，generation=1，任务SUCCEEDED、发布阶段active。
3. dense/keyword/hybrid各验证child/parent，6种查询均真实重排、没有降级、返回当前
   revision。验证的是链路、模式和版本，不据此声称生成答案准确率。
4. 对该active执行现有GC原语，必须抛ActiveRevisionDeletion；指针和检索继续有效。
5. API/IO关停后另起新进程，新IO明确就绪；重复提交仍返回已成功原任务，六种查询
   仍通过，可见revision保持不变。

移交仍只保存manifest、child文字和metadata，不重复保存parent正文或模型向量；准备
后按协议清空大正文，未绕开既有准备、激活、GC和资源托管。
响应丢失、superseded、GC部分失败及SIGKILL的可控故障注入仍由300条真实中间件
集成覆盖，其中模型替身用于控制时序；不冒充真实GPU服务或跨主机断电故障验收。

最终runner这次原生响应含完整60个物理页，第59/60页为空；规范化167573字符、58个
内容块。其摘要与33批两次独立解析不同，背封文字仍有间歇遗漏。保留原始wire和
源PDF身份，不将物理页齐全等同于OCR完整，亦不替换已冻结的质量评分输入。
数字记录见[演练回执](relay_20261026.json)。

前两次驱动尝试分别错误读取准备后已清空的大正文，以及把主动停止的API当作异常
死亡，导致验证中断；失败记录保留。修正只在私有演练驱动中按handoff/主动停止状态
观察，最终全过程通过。Uvicorn的SIGTERM退出码为-15，同时核验Application shutdown
complete；worker要求0退出及关闭日志。驱动采用posix_spawn，避免持有gRPC客户端时fork。

两次API退出分别出现40个semaphore的resource_tracker警告；根因未完成独立复现，
不能宣称全部日志资源已无警告。后续先用最小Uvicorn/队列日志程序复现，检查残留和
日志排空，再决定修复位置，不凭警告猜测而改变共享Context/日志所有权。
