# MinerU 4.0.12 与 Pro2605 独立验证

2026-10-27。**值得继续迁移验证，但不能直接升级生产或删除现有逐页补丁。**
原生 `FULL` 渲染保留背封、阻止跨页合并，已经具备替代部分部署补丁的能力；默认
V1 HTTP 导出仍没有等价的逐页 Markdown 契约。默认内容过滤、图片传输和资源预算
也有确认的差异。本轮只新增实验记录，应用、依赖锁、默认配置和索引均未切换。

## 固定范围与复现条件

- 独立 Python 3.12.13 环境正常安装 `mineru==4.0.12`，没有使用 `--no-deps`。
  实际解析栈为 `mineru-vl-utils==2.0.7`、`docvortex==0.6.4`、ONNX CPU 小模型。
  [123项依赖快照](mineru4_pro2605_20261027.requirements.txt)记录本机实际解析结果，
  不是跨平台或带全部 wheel 摘要的安装锁；Comet-RAG 环境未安装 MinerU。
- 上游 VLM 固定为9919、`opendatalab/MinerU2.5-Pro-2605-1.2B`；只读模型列表核验
  通过。远端未返回权重和 tokenizer 的不可变身份，不能把固定名称等同于固定字节。
- 显式选择 `advanced`、`ocr_mode=auto`、`page_range=all`，单文档任务、VLM并发2、
  处理窗口2，LLM辅助功能关闭。4.x 的 tier 不能直接等同于3.x backend；特别是
  `standard/high` 路径不会像 `advanced/xhigh` 一样启用图像分析。
- 使用独立 `MINERU_HOME`；本地小模型来自官方仓库
  `opendatalab/MinerU-4_models_onnx` 的修订
  `358310b4f64b95f9fefc372ad899356e4111f376`，13个资源文件逐一记录SHA-256。
  即使远端提供VLM，4.x仍会使用本地OCR、版面及按需加载的公式模型。
- 同一用户PDF工作区副本60页、9024767字节，SHA-256
  `e42f3b70cee6344ca8e0cb06ccc4028e56a05266cbd331c9e008fe05e62a2ffe`；
  公开NIST SP800-145/144整本7/80页，字节锁沿用 `evals/pdf/pages.json`。没有只解析
  旧标签所选12页，也没有走默认前10页的CLI入口。
- 保留此前3.4.5＋同一Pro模型的60页记录，并重新跑3.4.5的两份公开整本：7页
  11.09秒、80页133.84秒。新旧任务串行执行，避免本实验主动制造GPU争用。
  这不是随机交错、固定服务器负载的速度基准，不据单次耗时宣称全面提速。

## 背封：原生保留能力可用，默认过滤未解决

两个4.x完整60页结果的物理60页仍有8个 `footer` 块，默认Markdown为空；关闭图像
分析也不改变这一点。与原PDF背封目视对照，文字确实存在，不能按空白页判定成功。

原生 `FULL` 模式保留这些块，恢复288字符及3/3背封探针。说明这次无需自行OCR或
从另一个提取器拼字；但它没有修正“背封被分为页脚”的分类，而是改变渲染保留策略。
`FULL`也保留其他页眉、页脚和页码，原本只含页码的59页因此非空，不能将“无空页”
宣传为识别质量全面改善。是否将重复页元素纳入检索仍需另验。

## 逐页：可复用原生渲染，尚不能直接替代HTTP补丁

4.x Middle JSON使用 `schema=docvortex.middle`、`schema_version=2.0`，原生页面树
保留0基物理页号。四份成功ZIP均具备完整连续页域。按原生SDK逐页渲染 `FULL`，
以原生页面分隔符拼接后，与整本 `FULL` 逐字相同；`DEFAULT`逐页拼接则四份都不同，
因为默认视图仍会合并跨页续文等内容。

验证直接调用公共SDK，不复制上游排版器，也没有按文本相似度猜页或切分全文：

```python
from mineru.parser.base import ParseResult
from mineru.render import RenderMode, render_markdown

result = ParseResult.from_json(zip_middle_json)
fragments = [
    render_markdown(
        result.middle_json.model_copy(
            update={"pages": [page], "is_full_document": False}
        ),
        mode=RenderMode.FULL,
    )
    for page in result.pages
]
assert "\n\n---\n\n".join(fragments) == result.markdown(mode=RenderMode.FULL)
```

这段代码只在独立MinerU环境验证。原生分隔符不能直接套入现有Port的双换行拼接
契约；离线探针另构造显式的新逐页视图，并重新做规范化字符区间及页内分块核验，
没有声称它等于原生HTTP默认Markdown。

两个必须保留的边界：

1. V1 HTTP原生导出为Markdown、Middle JSON、structured content或ZIP，没有等价的
   `page_markdown` 导出项；实际请求返回400。HTTP Markdown也没有 `FULL` 参数。
   `/health`、`/tasks`返回404，当前应用客户端在上传前明确失败；新增的 `/v1/tasks`
   不是旧protocol v2的别名。不能只改URL、伪报health扩展或沿用旧响应解析。
2. 原生schema虽然拒绝错误身份、旧版本、bool页号和重复页号，但
   `is_full_document=true`仍可接受缺一物理页的结构。必须另外对照源PDF页数校验完整
   连续页域，不能把这个标志当作已经验收的页事实。

还核对了容易遗漏的替代路径：**原生HTTP `structured_content`已经提供完整pages及
每块的Markdown `content`字符串**，并单列图片来源、caption、footnote、标题level等。
四份产物的页域都正确，背封块也在其中；不能说4.x没有逐页原生输出。但它不等于
整页Markdown，直接拼接块content，四份均不能重建DEFAULT或FULL；它也没有Middle
JSON的schema身份，不能传给同一个反序列化器冒充相同协议。

若愿意明确采用新的结构化canonical，这是值得优先评估的另一条路：消费原生块和
页事实，重新定义规范化与证据契约，不再要求保持旧Markdown。它可能省去逐页部署
扩展，但须先核对标题、图片、说明和表格映射，不能临时在适配器里堆一个排版器。
本轮只验证能力及差异，没有变更Port、应用规范化或生产canonical。

因此，本轮样本表明原生FULL可承担旧补丁中的按页渲染和跨页合并约束；**现阶段不能据此
删除整个部署扩展或把4.x地址接给现有应用。** 后续优先争取上游V1直接提供物理页
Markdown及渲染模式，或验证上述原生结构化canonical方案；若仍需部署侧薄封装，
只复用原生renderer并显式协商新协议。
应用保持HTTP边界，不把MinerU或Docvortex运行时塞进Comet-RAG核心。

## 图像解读与文件资源

开启分析时，60页原生ZIP视图含43个解读块，其中6个 `chart`；关闭后解读块为0，
图表退为图片。物理22页图6输出带 `~` 的估计数值表，目视可确认对应原柱图，但
原图没有逐柱精确数字。这些是模型推断，不能充当已核准的逐字原文或精确表格金标。
关闭分析复用 `api-server --disable-image-analysis`，没有正则删说明或另写识图链路。

原生HTTP导出还有两项确认的资源差异：

- 60页开分析的独立Markdown响应17479093字节，图片使用data URI；关分析仍为
  17455238字节。两者都超过现有适配器16 MiB响应预算，关解读不能解决图片体积。
- 单独Middle JSON省略PDF图片字节，直接重渲染不能恢复HTTP原文；第一轮连解读块
  数也从HTTP的43变为37，因为缺少图片资产会影响图表渲染路径。不能将这种中间产物
  当作完整、可复现的内容包。
- 原生自包含ZIP保留sidecar，四份包都可逐字重渲染其默认Markdown。60页开分析包
  28006697字节，展开35743466字节，含52张sidecar及20183629字节Model JSON。
  ZIP并未自动变成小响应；迁移必须分别设计下载、解压、文件数量、资产和总deadline
  预算，不能只抬高现有上限。7/80页包分别123697/5567892字节。

## 验证与后续决定

本轮运行了10项独立原生schema／渲染检查、6项真实本机HTTP反例及3项反向注入。
把FULL误换DEFAULT、删除footer、改错一个指定表格单元，检查均按预期失败；最后
一项只剩23/24正确，证明没有靠全文随便找数字通过。错误协议／参数没有提交新任务。

现有消费者、部署及页审计134项定向单测通过；默认全量unit为3632 passed、15 skipped、
1 xfailed，389项其他标记未运行。pytest耗时10.47秒，**本次未满足小于10秒预算**；
不把功能通过写成性能门禁通过。没有改服务代码，未重跑无关中间件/E2E套件，也没有
把历史覆盖率冒充本轮结果。

三个自建API均在任务终止后SIGTERM关停，PID退出、监听端口关闭，9919上游未操作。
两个4.x API退出时各出现一次resource_tracker的“1个semaphore待清理”告警；观察到
进程退出不证明生命周期完全无问题，也尚未证明有持续OS泄漏，列入迁移前核查项。
